## In short

1. **Declare `languages`** in `doc.config.mjs`: the first is the source language — `content/` holds it, exactly
   as in a mono-language project — every other one is a translation. A project that never declares `languages`
   is strictly unchanged: no selector, no translations folder.
2. **Translate into `translations/<lang>/`**, a folder that mirrors `content/`'s own tree, file for file: pages,
   section introductions, `home.md`, `toc.json`, `glossary.json`, every file optional.
3. **One file, every language embedded**: the built site carries a language selector and switches without
   reloading; the address always carries the current language, `#/en/…`.
4. **Four states** compare a translated file with its source: `missing`, `unmarked`, `stale`, `current` —
   `doc-kit translate status` lists them.
5. **No LLM call from the kit**: a person, or the skill's `translate` brief, writes the page from the dossier
   `doc-kit context <page> --translate <lang>` builds. Marking a translation (`translate --mark`) is always a
   separate, deliberate step.

## Declaring the languages

```js
export default defineConfig({
  languages: ["en", "fr"],
});
```

- `languages[0]` is the source language; the site's own `language` is then derived from it.
- A section id, or the first segment of a page id, equal to a declared language is the blocking error
  `languages.idClash`, even with `--draft`: the URL grammar below reserves those segments.
- A fresh project can declare them at creation instead of hand-editing the configuration:
  `doc-kit init --languages fr,en` (`--lang` must then be absent or equal to the first of the list). Every
  language but the first starts with an empty `translations/<lang>/.sources.json`: nothing is pre-translated,
  and `translate status` lists every file as `missing` right after `init`.

## The translations folder

`translations/<lang>/` (`paths.translations`, default `"translations"`) mirrors `content/`, file for file:

- `toc.json`: the table of contents' **texts** only — `title`, `tagline`, sections' `title`/`shortTitle`/
  `subtitle`/`highlights`, groups' `title`, pages' `title`/`menuTitle`/`summary`, journeys' and spaces' own text
  fields. Every other field (ids, routes, permissions, `counterpart`, `spaces[].id`…) always comes from the
  **source**: a translated value that differs there is ignored, with a warning. A missing title falls back to
  the source silently (a partial translated `toc.json` is fine); a section, group, page, journey or space
  missing, added or reordered, or a different number of steps, is the blocking error `translation.toc.structure`
  — even with `--draft`, like an invalid outline.
- `glossary.json`: the same entries, in the same order; `term`, `def` and `pattern` translated, `technical`
  always from the source. A different number of entries is an error in a strict build, a warning with `--draft`
  (the source glossary is used in its place).
- `home.md`, `<section>/index.md`, `<page>.md`: the Markdown of that language — same syntax, same capture ids,
  same diagram ids, same rule ids as the source file they translate.
- `diagrams/<id>.svg`: a translated diagram; one without a translation is shared across every language.
- `.sources.json`: `{ "<file>": "<fingerprint>" }`, one entry per translated file — bookkeeping only, written
  solely by `translate --mark`. Never edit it by hand.

## The language selector and the URL

The built site adds a selector (top bar, or the head of the side menu on a narrow screen), one button per
declared language, labelled with its autonym, the current one marked. Every address gains an optional language
prefix: `#/[<lang>/]<path>`, for example `#/en/`, `#/en/@business`, `#/en/use/orders~approval`. A link written in
the Markdown, or generated by the site, never carries the prefix: it means "the language shown right now". After
routing such a link, the address bar is rewritten to carry the current language anyway, without adding a history
entry — so a shared or bookmarked address always names its language. A page translated only part way shows a
banner, "Not translated yet — shown in {language}", on a page, a section introduction or the home page built from
the source in its place (a `--draft` build only; a strict build refuses a missing translation outright, below).

## The four states of a translated file

| State | Meaning |
|---|---|
| `missing` | No file at all in `translations/<lang>/`. |
| `unmarked` | A file exists, but was never recorded by `translate --mark`. |
| `stale` | A file was marked, but its source has changed since (the recorded fingerprint no longer matches the source's current hash): translate it again. |
| `current` | Marked, and its source has not changed since. |

## Checking the state: `doc-kit translate`

```bash
doc-kit translate status [--lang <l>] [--check]
doc-kit translate --mark <page…> | --mark --all [--lang <l>]
doc-kit translate --fix-anchors [page…] [--lang <l>]
```

- **`status`**: for each language but the source (or just `--lang <l>`), every translatable file's state, the
  counts, then the files that are `stale` or `missing`. Exit code 0 always; `--check` makes it 1 when a listed
  language has a `stale` or `missing` file — a gate a project can add to CI.
- **`--mark <page…>`** or **`--mark --all`**: records the current fingerprint of each item's source into
  `translations/<l>/.sources.json`. An item is a page id, or a content-relative path when it contains a `.`
  (`home.md`, `use/index.md`, `toc.json`, `glossary.json`); `--all` marks every file whose translation exists.
  Marking an item whose translation file is missing fails that language (`translate.missingFile`, exit code 1)
  without writing anything for it; calling `--mark` with neither an item nor `--all` is a usage error (exit
  code 2).
- **`--fix-anchors [page…]`**: in each translated page, rewrites a link `#/<target>~<anchor>` whose anchor is a
  heading id of the **source** target page but not of the translated one, to the translated page's heading at
  the same position — only when both pages have the same number of headings. A link it cannot map is left as it
  is and reported (target not translated, a different heading count, or an anchor unknown to either page).
- Marking a translation never happens without `--mark`; the unrelated `doc-kit sync --mark` never touches
  `.sources.json`.

## Writing a translation: the dossier and the brief

```bash
doc-kit context use/orders --translate fr
```

Writes the translator's dossier, without any application code: the page's id, titles (source and translated),
template, source and target file, and its state; the headings to write, already in the target language, taken
from the page's template; a glossary table, source term → translated term, for the terms whose pattern matches
the page; the whole source Markdown; the previous translation, whole, when one exists; and, in a documentation
project that is a git repository, the diff of the source since the fingerprint `translate --mark` last recorded
— one line saying there is none otherwise. `--translate <lang>` is exclusive with `--update` (the writer's own
context), and refuses the source language or an undeclared one (exit code 2 either way). `--budget` only ever
cuts the diff, then the previous translation: the page, its sections, the glossary and the source are never cut.

The skill's `translate` brief (variables `{{lang}}`, `{{pages}}`, `{{contextFiles}}`; agent `doc-kit-writer`)
reads that dossier and at most one further file (the source page, in full, when the dossier alone is not enough)
per page, keeps every heading, directive, id, badge, code span, proof and capture id exactly as the source has
them, translates only the prose, then runs `translate --fix-anchors`, `translate --mark`, and a `build --draft`
on the batch it just wrote.

## Building and capturing per language

`doc-kit build` always writes the multilingual file, every language embedded; two options give a single one:

- **`doc-kit build --lang <l>`**: a mono-language file, the configured output with `-<l>` before its extension
  (`Acme-Orders-Documentation.html` → `Acme-Orders-Documentation-fr.html`; `--output` overrides it). Its data is
  exactly what the multilingual file embeds for `<l>`, without the other languages.
- **`doc-kit capture --lang <l>`**: takes the plans with `capture.languages.<l>` (`locale`, `cookies`, `storage`,
  each merged over the top-level `capture.locale`/`capture.cookies`/`capture.storage`; `locale` defaults to that
  language's own locale) and writes `<images>/<l>/<id>.webp` and `<images>/<l>/zones/<id>.json`. A capture
  without a file for `<l>` is shared: every language shows the source image and its zones. `check images` and
  `optimize` also walk `<images>/<l>/`.

`doc-kit view --lang <l>` and `doc-kit open --lang <l>` open the site on `#/<l>/…`; `doc-kit dev` also watches
`<paths.translations>/`.

## The update cycle

The whole point of the fingerprint recorded by `translate --mark` is that only the pages whose **source** changed
since the last mark need a translator's attention: `doc-kit translate status` shows them, and only them, as
`stale` — a page whose source is untouched stays `current` even months later. `doc-kit sync`'s own report gains a
`translations` category the same way, listing every `stale` and `missing` file without touching git, and
`doc-kit doctor` prints one summary line per language (`⚠` once any file is stale or missing, `✖` when
`translations/<l>/toc.json` itself is missing); the guided mode offers `translate status` as its next step under
the same condition. `doc-kit audit` adds a "Translations" table (language, current, stale, missing, and the
ratio of current files to the total) — informative only, it never changes the maturity level.

## Pitfalls and observed gaps

> [!WARNING] A structural mismatch blocks even a draft build
> Adding, removing or reordering a section, group, page, journey or space in a translated `toc.json` is
> `translation.toc.structure`, blocking whatever the build mode — only the source table of contents may change
> structure; a translation only ever supplies different text for the same shape.

> [!NOTE] An unmapped anchor is reported, not guessed
> `translate --fix-anchors` rewrites an anchor only when the source and the translated target page have the
> exact same number of headings; otherwise it leaves the link as it is and names the reason
> (`translate.anchorUnmapped`). Translating the target page first, then rerunning `--fix-anchors`, is the usual
> fix.
